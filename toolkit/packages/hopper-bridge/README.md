# @rtk/hopper-bridge

**UNVERIFIED against real Hopper: Hopper is not installed in this environment, so nothing in this package has ever run against Hopper Disassembler.** What exists is a Node client + provider adapter for a documented bridge protocol, and a Python bridge script whose protocol layer is tested under plain `python3`, but whose Hopper API calls are unverified sketches that raise `NotImplementedError` outside Hopper.

## Contents
- `src/protocol.ts`: the rtk-hopper protocol v1 (documented in the header comment): newline-delimited JSON over a Unix socket in a private 0700 directory, socket mode 0600, first message must be `auth` with a per-session random 256-bit token, request ids, error codes (`auth_failed, bad_request, unknown_method, not_implemented, not_open, internal`), 8 MiB line limit.
- `src/client.ts`: `HopperClient.connect({socketPath, token})` verifies socket type/mode/owner and directory mode before sending the token; request/response matching by id, per-request timeout, connection loss/protocol errors reject pending requests.
- `src/launcher.ts`: `launchBridge({bin, args, script})` creates the private dir, token file (0600) and starts the host process in its own process group; `stop()` SIGKILLs the group and removes the dir (verified). The real Hopper command line for running a script is **unknown/unverified**, so there is no default: the caller supplies `bin` and `args`.
- `src/provider.ts`: `HopperProvider` (id `hopper`, kind `deep`) implementing the `@rtk/provider-router` `AnalysisProvider` interface. Operations forwarded to the bridge: `binary_overview, list_procedures, procedure_info, list_strings, search_strings, xrefs, procedure_callers, procedure_callees, procedure_pseudo_code`. Returns evidence (provider `rtk-hopper-bridge`) whose limitations always state it is unverified. On `open` it checks the protocol version and that the bridge's document sha256 equals the target's. It reports `unavailable` unless a launch command or connection is configured.
- `bridge/hopper_bridge.py`: Python server for the protocol. Hopper API calls are tagged `UNVERIFIED`; outside Hopper (no `Document` global) they raise `NotImplementedError` (protocol code `not_implemented`). `open_document`, `procedure_info`, `list_strings`, `search_strings`, `xrefs`, `procedure_callers`, `procedure_callees` are not implemented at all (always `not_implemented`).

## Verification (`npm test`, 12 tests, no Hopper needed)
Against a fake Hopper server written in `test/fakeHopper.ts`: auth success, wrong-token failure, request/response and concurrent id matching, remote errors, request timeout with late reply ignored, silent server, garbage reply, server death, refusal of non-0600 sockets and non-private directories, provider open/call/close lifecycle and cleanup, sha256 mismatch rejection, provider-router integration, no-fallback when unavailable. Against the real `bridge/hopper_bridge.py` under `python3` (skipped if python3 is missing): launch, socket/dir/token permissions, token auth, protocol errors, `not_implemented` outside Hopper, shutdown, process-group kill and temp-dir cleanup, refusal to bind in a non-private directory, early host exit.

## Not verified / not done
The Hopper Python API usage, how Hopper is launched with a script, whether Hopper allows a listening socket in its embedded interpreter, headless operation, document loading and sha256 verification inside Hopper, and every analysis result's correctness against Hopper. Expect to rewrite the `Backend` class against real Hopper.
